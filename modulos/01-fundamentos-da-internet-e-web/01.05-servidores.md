# Servidores

## Objetivo

Ao final desta aula, você deve ser capaz de:

- explicar o que é um servidor no contexto da Web;
- diferenciar servidor como máquina, programa e papel;
- entender como servidores respondem requests;
- reconhecer tipos comuns de servidores e ambientes onde eles podem existir;
- reconhecer, em alto nível, formas comuns de hospedagem;
- reconhecer exemplos de servidores em aplicações reais.

## Ideia Central

Servidor pode significar mais de uma coisa.

Às vezes, falamos de servidor como uma máquina. Às vezes, como um programa que escuta requests. Às vezes, como o papel de responder a um cliente.

No desenvolvimento web, o mais importante no começo é entender a responsabilidade: um servidor recebe pedidos, processa esses pedidos e devolve respostas.

Um servidor pode existir no seu computador durante o desenvolvimento, em uma
máquina física de uma empresa, em um data center, em uma máquina virtual na
cloud ou por trás de uma plataforma que esconde boa parte da infraestrutura.

Neste momento, você não precisa escolher uma arquitetura de hospedagem. O
objetivo é reconhecer os nomes principais para não imaginar que "servidor" é
sempre uma única caixa física ligada à Internet.

## Tipos Comuns de Servidores

Na prática, a palavra servidor pode aparecer acompanhada de várias funções:

| Tipo | O que faz |
| --- | --- |
| **Servidor web** | Recebe requests HTTP e devolve páginas, arquivos ou encaminha pedidos para outra aplicação. |
| **Servidor estático** | Entrega arquivos prontos, como HTML, CSS, JavaScript, imagens e fontes. |
| **Servidor de aplicação** | Executa regras da aplicação, processa dados e monta respostas dinâmicas. |
| **Servidor de API** | Expõe dados e operações para clientes, geralmente devolvendo JSON. |
| **Servidor de banco de dados** | Armazena e consulta dados persistentes para a aplicação. |
| **Proxy ou reverse proxy** | Fica no caminho entre cliente e servidor, encaminhando requests e aplicando regras. |
| **CDN** | Distribui arquivos e respostas a partir de servidores próximos dos usuários. |

Esses nomes não significam que sempre existem máquinas separadas. Em um projeto
pequeno, uma única máquina pode executar vários papéis. Em sistemas maiores,
cada papel pode ser separado para melhorar escala, segurança e operação.

## Onde Servidores Podem Viver

Servidores precisam existir em algum ambiente físico ou virtual:

- **Computador local:** usado durante desenvolvimento e estudo. Seu notebook pode
  rodar um servidor local para testar uma aplicação.
- **On-premises:** servidores mantidos pela própria empresa, em sua sede ou em
  uma sala técnica controlada por ela.
- **Data center ou colocation:** servidores ficam em instalações especializadas,
  com energia, refrigeração, rede e segurança física.
- **Cloud:** recursos alugados de um provedor, como máquinas virtuais, bancos
  gerenciados, armazenamento, CDNs e plataformas de aplicação.
- **Edge ou CDN:** servidores distribuídos geograficamente para entregar conteúdo
  mais perto dos usuários.

Cloud não elimina servidores. Ela muda quem compra, opera, mantém e disponibiliza
esses recursos.

## Formas Comuns de Hospedagem

Hospedar uma aplicação significa colocá-la em um ambiente onde ela possa ser
acessada pelos clientes certos.

Neste módulo, o objetivo é apenas reconhecer três ideias:

- **Hospedagem compartilhada:** vários sites dividem a mesma infraestrutura. É
  simples, mas oferece menos controle.
- **Servidor próprio ou máquina virtual:** você tem mais controle sobre o ambiente,
  mas também assume mais configuração e manutenção.
- **Plataformas e serviços gerenciados:** você entrega parte da aplicação ou dos
  dados para uma plataforma que cuida de mais detalhes de execução, escala e
  operação.

Essas opções serão aprofundadas em módulos futuros. Por enquanto, guarde a ideia:
servidor pode ser papel, programa, máquina, ambiente ou serviço gerenciado,
dependendo do contexto.

Termos como VPS, servidor dedicado, PaaS, serverless, bancos gerenciados e CDN
voltarão com mais calma nos módulos de backend, deploy, cloud e DevOps. Não é
necessário dominar essas diferenças agora.

## Exemplo Prático

O portal do PetCare OS pode ser servido de formas diferentes.

Um servidor estático devolve arquivos prontos:

- HTML
- CSS
- JavaScript
- imagens do logotipo e ícones

Um servidor dinâmico do PetCare OS pode:

- validar o login do tutor;
- buscar o status do pet em um banco de dados;
- calcular o total de um orçamento;
- registrar uma aprovação de orçamento;
- devolver JSON para o frontend montar a tela.

Em um ambiente simples, tudo isso poderia rodar em uma única máquina virtual.
Em um ambiente mais maduro, arquivos estáticos, API e banco de dados poderiam
ficar em serviços diferentes.
O conceito central continua o mesmo: clientes fazem pedidos e servidores devolvem
respostas.

## Analogias e Intuições

- Servidor é quem atende pedidos dentro de uma comunicação.
- Uma mesma máquina pode rodar vários programas servidores.
- Um servidor não precisa ser "grande"; até seu computador pode rodar um servidor local para desenvolvimento.
- Hospedagem é como escolher onde uma loja vai funcionar: pode ser uma sala própria, um espaço alugado, um shopping com infraestrutura pronta ou uma operação em vários pontos de entrega.
- Cloud é alugar infraestrutura pronta, não fazer a aplicação deixar de depender de computadores reais.

## Erros Comuns

- Achar que servidor é apenas um computador físico.
- Confundir servidor com backend, mesmo quando há sobreposição.
- Pensar que todo servidor precisa gerar páginas completas.
- Esquecer que servidores também podem devolver arquivos estáticos.
- Imaginar que o servidor sempre sabe quem é o usuário sem receber alguma informação.
- Achar que cloud significa "não existem servidores".
- Tentar decorar todos os tipos de hospedagem antes de entender o papel básico de um servidor.
- Pensar que CDN substitui toda a aplicação. Ela pode entregar conteúdo e acelerar acesso, mas nem sempre executa todas as regras do sistema.
