## Ideia Central

HTTP é o protocolo mais importante para entender a comunicação da Web.

Ele define como clientes e servidores trocam mensagens. Uma request HTTP pede algo. Uma response HTTP devolve o resultado desse pedido.

No início, não é preciso decorar todos os métodos, headers e status codes. O essencial é entender a estrutura da conversa e conseguir observar essa conversa nas ferramentas do browser.

## HTTP vs HTTPS

HTTP define o formato da conversa entre cliente e servidor: como pedir um
recurso, como responder, como indicar metadados e como comunicar o resultado.

HTTPS é HTTP trafegando por uma conexão protegida por TLS. Essa proteção ajuda a:

- criptografar os dados durante o caminho;
- reduzir o risco de alguém ler a comunicação;
- verificar se o cliente está falando com o servidor esperado;
- detectar alterações indevidas na comunicação.

Na prática, quando você vê `https://`, a conversa HTTP continua existindo, mas
ela acontece dentro de uma camada de proteção.

HTTPS não torna uma aplicação automaticamente correta ou segura em todos os
sentidos. Ele protege a comunicação no transporte, mas a aplicação ainda precisa
validar dados, controlar acesso, proteger senhas e lidar com erros corretamente.

## Verbos HTTP

Os verbos HTTP, também chamados de métodos HTTP, indicam a intenção da request.
Eles ajudam cliente e servidor a combinarem o tipo de ação desejada.

| Método | Intenção comum | Exemplo no PetCare OS |
| --- | --- | --- |
| **GET** | Buscar ou ler um recurso. | Buscar o status de um pet. |
| **POST** | Enviar dados para criar algo ou disparar uma ação. | Enviar um formulário de login. |
| **PUT** | Substituir um recurso inteiro. | Atualizar todos os dados de cadastro de um tutor. |
| **PATCH** | Alterar parcialmente um recurso. | Atualizar apenas o telefone do tutor. |
| **DELETE** | Remover um recurso. | Excluir um registro permitido pelo sistema. |
| **HEAD** | Buscar apenas os headers, sem body. | Verificar metadados de um recurso sem baixar o conteúdo. |
| **OPTIONS** | Perguntar quais operações ou opções estão disponíveis. | Descobrir quais métodos um endpoint aceita. |

Esses nomes não executam mágica sozinhos. O servidor precisa implementar o
comportamento correto para cada rota. Ainda assim, usar métodos coerentes ajuda
a tornar APIs e aplicações mais previsíveis.

## Status Codes

Status codes são códigos numéricos enviados na response para resumir o resultado
da request.

Você não precisa decorar todos. O mais importante no começo é reconhecer as
categorias:

| Categoria | Significado geral | Exemplos |
| --- | --- | --- |
| **1xx — Informação** | A request foi recebida e o processo continua. | `100 Continue` |
| **2xx — Sucesso** | A request foi processada com sucesso. | `200 OK`, `201 Created`, `204 No Content` |
| **3xx — Redirecionamento** | O cliente precisa seguir outro caminho ou pode reutilizar algo. | `301 Moved Permanently`, `302 Found`, `304 Not Modified` |
| **4xx — Erro do cliente** | A request tem algum problema do lado de quem pediu. | `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found` |
| **5xx — Erro do servidor** | O servidor falhou ou não conseguiu concluir a request. | `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable` |

Alguns exemplos comuns:

- `200 OK`: deu certo e há uma resposta.
- `201 Created`: algo foi criado.
- `204 No Content`: deu certo, mas não há conteúdo no body.
- `301` ou `302`: o recurso está em outro lugar.
- `304 Not Modified`: o recurso não mudou em relação ao que o cliente já tinha.
- `400 Bad Request`: a request veio em formato inválido ou incompleto.
- `401 Unauthorized`: falta autenticação válida.
- `403 Forbidden`: o cliente foi identificado, mas não tem permissão.
- `404 Not Found`: o recurso não foi encontrado.
- `500 Internal Server Error`: erro inesperado no servidor.

## Exemplo Prático

Uma request do portal do PetCare OS pode pedir o status de um pet:

```text
GET /api/pets/123/status HTTP/1.1
Host: app.petcareos.com.br
```

Uma response simplificada poderia ser:

```text
HTTP/1.1 200 OK
Content-Type: application/json

{
  "petId": "123",
  "nome": "Thor",
  "status": "Em Triagem"
}
```

O cliente pediu o recurso `/api/pets/123/status`. O servidor respondeu com sucesso e informou que o conteúdo é JSON.

Outras requests poderiam ter intenções diferentes:

```text
POST /api/login HTTP/1.1
Host: app.petcareos.com.br
Content-Type: application/json

{
  "email": "tutora@example.com",
  "senha": "..."
}
```

```text
PATCH /api/tutores/42 HTTP/1.1
Host: app.petcareos.com.br
Content-Type: application/json

{
  "telefone": "(11) 99999-9999"
}
```

E o servidor poderia responder com resultados diferentes:

```text
HTTP/1.1 201 Created
```

```text
HTTP/1.1 401 Unauthorized
```

```text
HTTP/1.1 404 Not Found
```

O método mostra a intenção do pedido. O status code resume o resultado.

## Analogias e Intuições

- HTTP é a regra da conversa entre cliente e servidor na Web.
- Método é a intenção do pedido.
- Status code é um resumo do resultado.
- Header é metadado sobre a mensagem.
- Body é o conteúdo principal quando existe.
- HTTPS é como fazer a mesma conversa dentro de um canal protegido.
- A família do status code já dá uma pista: `2xx` costuma indicar sucesso, `4xx` problema na request e `5xx` falha no servidor.

## Erros Comuns

- Achar que HTTP é a mesma coisa que HTML.
- Decorar status codes sem entender a categoria geral.
- Confundir método HTTP com rota.
- Achar que GET, POST, PUT, PATCH e DELETE são apenas nomes livres, sem intenção semântica.
- Usar POST para tudo sem pensar no significado da operação.
- Confundir `401` com `403`: um fala de autenticação ausente ou inválida; o outro, de permissão negada.
- Achar que HTTPS resolve todos os problemas de segurança da aplicação.
- Ignorar headers porque eles parecem detalhe.
- Não perceber que HTTP, por padrão, não lembra automaticamente requests anteriores.
